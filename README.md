# 🎾 MatchPoint — теннисные турниры для компании друзей

Android-приложение для организации любительских теннисных турниров: создание турнира,
автоматическая генерация сетки/групп, ведение счёта матча администратором в реальном времени
и профили игроков со статистикой.


## Как открыть

1. Открой Android Studio (Iguana/Koala или новее) → **Open** → выбери папку `MatchPoint`.
2. Дай Gradle синхронизироваться (первый раз скачает зависимости — нужен интернет).
3. Если Android Studio попросит создать `local.properties` — она сделает это сама и пропишет
   путь к вашему Android SDK.
4. Запусти на эмуляторе или устройстве с **API 26+** (compileSdk/targetSdk = 34).

Минимальная версия — 26, потому что задание требует API 34, а более широкий minSdk обычно
считается плюсом на собеседовании (показывает, что вы думаете о реальных пользователях).
При желании легко поднять `minSdk` до 34 в `app/build.gradle.kts`.

## Стек технологий

- **Kotlin + Jetpack Compose** (Material 3) — вся вёрстка декларативная, без XML-layout'ов.
- **MVVM + Clean Architecture**: `data` / `domain` / `ui`, доменный слой не знает про Room и Compose.
- **Room** — локальное хранение (игроки, турниры, участники, матчи), реактивные запросы через `Flow`.
- **Hilt** — dependency injection (ViewModel'и, репозитории, DAO).
- **Navigation Compose** — навигация между экранами с передачей аргументов (id турнира/матча/игрока).
- **Kotlin Coroutines / Flow** — вся асинхронность и реактивность.
- **DataStore (Preferences)** — пример современного хранения простых настроек (задел под "мой профиль").
- **JUnit** — unit-тесты на чистую бизнес-логику (генератор сетки, круговая система, счёт в теннисе).

## Архитектура

```
domain/            — чистый Kotlin, без Android-зависимостей
  model/           — Player, TournamentFormat, StandingRow, PlayerStats...
  scheduling/      — RoundRobinScheduler, GroupSplitter, BracketGenerator
  scoring/         — TennisScoreEngine — полноценный теннисный счёт (0/15/30/40, deuce/ad, тай-брейк, сеты)
  usecase/         — TournamentProgressPlanner (что создать дальше), StandingsCalculator
  repository/      — интерфейсы репозиториев (инверсия зависимостей)

data/
  local/           — Room: Entity, Dao, AppDatabase
  repository/      — реализации репозиториев, "склеивают" Room + domain-логику
  preferences/     — DataStore

ui/
  theme/           — тема Material3 в теннисной палитре (корт/мяч)
  navigation/      — NavGraph, экраны + нижняя навигация с FAB "+"
  home/ players/ playerprofile/ createtournament/ tournamentdetail/ match/
  components/      — переиспользуемые composable (автокомплит игрока, анимации, карточки)
```

Ключевая идея: **domain-слой полностью тестируется без Android** — вы можете запустить
`app/src/test/.../domain/*Test.kt` в обычной JVM, без эмулятора. Это специально выделено,
чтобы на собеседовании было что показать по теме тестирования.

## Логика турнира (то, что обычно спрашивают на собеседовании)

- **Круговая система** — классический алгоритм "circle method": фиксируем одного игрока,
  остальных вращаем по кругу. Работает для чётного и нечётного числа игроков (добавляется bye).
- **Группы + плей-офф** — игроки случайно распределяются по группам (~4 человека), внутри группы
  играют круговую систему, топ-1/топ-2 из каждой группы выходят в сетку на выбывание.
- **Плей-офф на выбывание** — если число игроков не степень двойки, сетка достраивается "баями"
  (автоматический проход в следующий круг) для сильнейших по посеву.
- Вся эта логика вынесена в **чистые функции** (`TournamentProgressPlanner`, `RoundRobinScheduler`,
  `BracketGenerator`) — репозиторий (`TournamentRepositoryImpl.advanceTournament`) только
  дёргает их и сохраняет результат в Room, когда очередной матч завершается.

## Счёт матча

Реализован настоящий теннисный счёт, а не упрощённый "первый до N очков":

- Очки внутри гейма: 0 → 15 → 30 → 40 → выигрыш (с учётом deuce/advantage).
- Гейм выигрывается с разницей минимум 2 очка.
- Сет — до 6 игр с разницей 2; при 6:6 включается тай-брейк до 7 (с разницей 2).
- Матч — до 2 побед в сетах (по умолчанию), либо один решающий сет — настраивается при создании турнира.
- Как только у кого-то фиксируется победа в матче — статус матча меняется на `FINISHED`,
  и `TournamentRepositoryImpl` автоматически проверяет, не нужно ли сгенерировать следующий
  раунд плей-офф или объявить победителя турнира.

Осознанное упрощение: не реализован "решающий тай-брейк" вместо третьего сета (используется
обычный третий сет) — это легко добавить отдельным флагом в `MatchRules`, но раздувало бы объём
для демо-проекта.

## Анимации

- **Начало матча** — две ракетки (иконки) "съезжаются" с краёв экрана и встречаются в центре,
  мячик подпрыгивает — `ui/components/TennisAnimations.kt: MatchStartAnimation`.
- **Победа в матче** — увеличивающийся кубок, плавное появление текста "Имя победил",
  падающие "мячики-конфетти" на фоне — `MatchWinnerAnimation`.
- Обе анимации написаны на чистом Compose (`animateFloatAsState`, `rememberInfiniteTransition`,
  `spring`), без внешних GIF/Lottie — специально, чтобы показать владение анимационным API Compose.

## Что можно показать на собеседовании отдельно

- Чистое разделение domain/data/ui и то, что бизнес-правила покрыты unit-тестами без Android.
- `TennisScoreEngine` — маленький, но полноценный конечный автомат (state machine) с иммутабельным
  состоянием — хорошая тема для разговора про функциональный подход к состоянию в приложении.
- `TournamentProgressPlanner` — как обрабатывается "разветвление" бизнес-логики в зависимости
  от формата турнира без нагромождения if/else в UI или в Room-слое.
- Room с `Flow`-запросами и автоматическим обновлением UI при изменении данных (reactive UI).
- Hilt DI, `@HiltViewModel`, `SavedStateHandle` для аргументов навигации.

## Возможные улучшения (если спросят "а что бы вы добавили")
